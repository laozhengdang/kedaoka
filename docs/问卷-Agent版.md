# 老郑荡的妙妙小工具 · 使用问卷（Agent 版）

> **给谁**：同学电脑上的 AI 编码助手（能执行命令的那种）
> **任务**：在这台机器上把工具装起来、真的跑一遍、按固定格式交回一份评测报告
> **产出**：一份 JSON（机器可汇总）+ 一段人话摘要（给作者看）
>
> 如果你（agent）只能聊天、不能执行命令，请直接告诉用户：
> 「这个问卷需要能跑命令的助手，我做不了」，不要编造结果。

## 〇、先读这几条红线

1. **不要上传用户的课件、卡片、截图到任何地方。** 报告里只写文字结论。
2. **所有测试都用临时数据目录**，不要碰用户已有的数据：

5. 装不上就**如实说装不上**，并给出卡在哪里、报什么错。不要猜。

## 一、准备：先问用户一个问题

> 「你是想**用**这个工具，还是想帮我**测**它？」

- 想用 → 不要装开发环境，直接走 **路径 A**
- 想测 / 想改代码 → 走 **路径 B**（测完仍然推荐路径 A 给日常用）

### 路径 A：下载成品包（推荐，2 分钟）

1. 打开 https://github.com/laozhengdang/miaomiao-study/releases/latest
2. 下载 `miaomiao-study-v0.9.1.zip`（约 178 MB）
3. 解压到 `C:\Temp\miaomiao-eval\app\`
4. 记下 `老郑荡的妙妙小工具.exe` 的完整路径

**注意**：GitHub 的附件走 `objects.githubusercontent.com`，国内可能连不上。
连不上就告诉用户「需要换网络下载」，不要去第三方站点找。

### 路径 B：从源码跑

```bash
git clone https://github.com/laozhengdang/miaomiao-study.git
cd miaomiao-study
npm install          # Node 22+，国内先设 ELECTRON_MIRROR
pip install pymupdf  # Python 3.10+
npm start
```

仓库根目录有 `AGENTS.md`，里面写了依赖版本、国内镜像和常见报错，先读它。

## 三、还要评估的三件事（主观，但要给理由）

### 3.1 产品形态（10 分）

问自己：**「这是一个能日常用的工具，还是一个演示品？」**
看：打开就有事可做吗？功能之间是否连贯（导入→复习→考前）？有没有明显断裂的环节？

### 3.2 页面布局（10 分）

看：三栏布局是否合理？功能按钮是否好找？信息密度是否过高/过低？
有没有「想找的功能得翻半天」的情况？记下具体是哪一页。

### 3.3 功能齐全度（10 分）

看：一个学生从「拿到课件」到「进考场」的完整链路，有没有明显缺口？
**不要拿市面上成熟软件的功能来比**（比如同步、多端、社区题库），只评「这条链路」是否够用。

## 四、输出格式（严格照这个来）

### 4.1 JSON（放在报告最前面）

```json
{
  "meta": {
    "agent": "你的名字/模型",
    "os": "Windows 11 23H2",
    "install_path": "A（成品包）/ B（源码）",
    "app_version": "v0.9.1",
    "data_dir": "C:\\Temp\\miaomiao-eval\\data",
    "tested_at": "2026-10-22T10:00:00+08:00"
  },
  "scores": {
    "product_form": 0,
    "layout": 0,
    "completeness": 0,
    "stability": 0
  },
  "results": [
    { "id": "A1", "status": "pass", "actual": "窗口标题 老郑荡的妙妙小工具", "evidence": "" },
    { "id": "F2", "status": "fail", "actual": "输出 33.33 m/s", "evidence": "shots/f2.png" }
  ],
  "bugs": [
    {
      "summary": "一句话说清问题",
      "severity": "blocker | major | minor",
      "steps": ["第一步", "第二步"],
      "expected": "应该怎样",
      "actual": "实际怎样",
      "repro": "always | sometimes | once",
      "evidence": "shots/xxx.png"
    }
  ],
  "missing_features": [
    { "what": "你觉得缺什么", "why": "为什么需要", "priority": "high | medium | low" }
  ],
  "layout_notes": [
    { "page": "课程页", "problem": "12 个彩色按钮一眼看不过来", "suggestion": "分组或折叠" }
  ],
  "verdict": "一句话总评"
}
```

**状态只能是这三种**：`pass` / `fail` / `blocked`（blocked = 前置条件不满足，比如下载不了）。
**没测的条目不要写 pass，写成 blocked 并说明原因。**

### 4.2 人话摘要（放在 JSON 后面）

按这个结构写，**不超过 600 字**：

```
【结论】能不能日常用：能 / 勉强 / 不能，因为……
【卡住的地方】按严重程度列 1-3 条，每条一句
【功能缺口】1-3 条
【布局问题】按页面列，每条带一句建议
【做得好的地方】1-2 条（别全是批评，作者需要知道哪些要保持）
【最该先修的一件事】
```

## 五、评分口径

| 分数 | 含义 |
|---|---|
| 9-10 | 成熟产品水准，可以直接推荐给别人 |
| 7-8 | 能日常用，有小毛病不影响主线 |
| 5-6 | 能用，但有明显断裂或需要绕路 |
| 3-4 | 只能演示，实际不好用 |
| 0-2 | 跑不起来 / 主线跑不通 |

**打分要给理由，只说分数不给理由的，作者没法改。**

## 六、如果你自己也发现了 bug（不在这份清单里）

直接加到 `bugs` 数组，格式照上。**优先级最高的三种问题**：

1. 数据错（算错、存错、丢了）
